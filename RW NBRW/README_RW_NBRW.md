# RW NBRW Regulatory Lists

National Bank of Rwanda (BNR / NBRW) — Jira DECD-6292. The bnr.rw site is a React SPA: each supervision page's "chart of documents" is served by a JSON endpoint (`/fsbs`, `/fsmf`, `/fsins`, `/fspens`, `/fsps`). The scraper resolves each target document **by name** on the endpoint (pdf filenames change with every monthly re-upload, e.g. `...-April_2026_DG6v9R9.pdf`), downloads the pdf with `requests`, and parses it — no Selenium needed.

## Notes

- RegulationType = `Regulated` for all rows (all lists are positive/licensed registers).
- Lists 1 and 5 render every data cell as vector glyphs with no extractable text (only the page title / column headers are real text) → `extract_table_rows_ocr` uses img2table + TesseractOCR per project convention; runs on the Windows production box (`Tesseract-OCR\` at repo root). Parsers identify rows by name, not by the tiny running-number cells, which OCR unreliably.
- **Gotcha (caused an initial control-room rejection, all rows blank for lists 1 & 5):** `Img2TablePDF(pdf_path)` must be called with `pdf_text_extraction=False`. img2table's default (`True`) trusts the pdf's embedded text layer over OCR whenever it finds *any* real text on the page — here that's just the title/headers — and silently skips Tesseract entirely, leaving every data cell blank. Confirmed by re-extracting both pdfs with `pdf_text_extraction=False`: all 11 banks (list 1) and all pension-provider rows (list 5) OCR correctly.
- **Gotcha (control server shipped list 5 with only 3 entities):** the shared OCR helper used to try the bordered detector first and fall back to `borderless_tables=True` only when it got **0** rows. On the Mac the bordered pass does return 0 for list 5, but on the control server it returns a small non-empty fragment of the grid, so the fallback never fired and only ~3 entities came out. List 5's grid is drawn as filled rects with zero stroked lines (pdfplumber: 358 rects, 0 lines), so the borderless detector is the only reliable one for it. Fix: list 5 now routes through `extract_table_rows_ocr_borderless` (borderless first), and the helper retries the *other* detector whenever a pass yields fewer than 5 raw rows, keeping the larger result. Each pass logs `[OCR] borderless_tables=...: N raw rows`, so the control-server run log now shows exactly which detector produced the data.
- **Gotcha (list 5 section mislabeling):** `parse_list5_pension`'s section-header matching must tolerate OCR concatenating the header words with no space (e.g. "CORPORATETRUSTEE", "INVESTMENTMANAGERS"), and must map to a canonical section name rather than title-casing the raw OCR match (which would otherwise produce "Corporatetrustee" / "Investmentmanagers"). Without this, the Corporate Trustee row and all 4 Investment Managers rows get the wrong (or blank) `License_Type`. Verified against the ground-truth pdf: 14 rows total — 1 Corporate Trustee, 6 Administrators, 4 Investment Managers, 3 Custodians.
- Some source typos are kept verbatim (e.g. MMI's e-mail `unfo@mmi.gov.rw`, Old Mutual's `...@oldmutal.rw`).
- List 6 title says "Licensed Institutions as of June 2026 (or most recent year)" — the name match `Licensed Institutions as of` + newest `date_last_modified` keeps it current.
